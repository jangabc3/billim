# 빌림 (Billim) — 프로젝트 개발 문서

> 여러 공공기관에 흩어진 대여·예약 정보를 한곳에서 검색하고, 발견한 자원은 공식 예약처로 연결하거나(외부 데이터) 직접 예약까지 처리하는(제휴 기관) 생활 밀착형 공공자원 플랫폼

**1인 개발 기준 문서입니다.** 팀 프로세스(디자인 협업, PR 리뷰어, 스프린트 회고)를 그대로 따라가지 않고, 혼자서도 같은 품질의 산출물을 남기는 방식으로 조정했습니다.

---

## 1. 요구사항 명세

### 1.1 문제 정의
공공기관은 생활 공구, 면접 정장, 휠체어, 체육시설 등 다양한 자원을 무료 또는 저렴하게 대여·예약할 수 있게 제공하지만, 정보가 기관별·플랫폼별로 흩어져 있어 존재 자체를 모르는 경우가 많다.

### 1.2 핵심 사용자 스토리
| 우선순위 | 스토리 |
|---|---|
| P0 | 사용자로서, 내 위치 주변에서 대여 가능한 자원을 카테고리·거리·무료 여부로 검색하고 싶다 |
| P0 | 사용자로서, 자원 상세 화면에서 출처와 최근 갱신 시각을 확인하고 공식 예약처로 이동하고 싶다 |
| P1 | 사용자로서, 관심 자원을 저장하고 나중에 다시 찾아보고 싶다 |
| P1 | 사용자로서, 신청 시작·마감을 놓치지 않도록 알림을 받고 싶다 |
| P1 | 제휴 기관 관리자로서, 물품과 재고를 등록·관리하고 예약을 승인·처리하고 싶다 |
| P2 | 사용자로서, 정보가 틀렸을 때 제보하고 싶다 |

### 1.3 스코프 경계 (중요 — 처음에 명확히 안 하면 계속 흔들림)
- **포함**: 공유누리·서울시 공공서비스예약 데이터 통합 검색, 공식 예약처 연결, 제휴 기관(빌림 자체 관리) 직접 예약, 관심 저장, 알림, 제보
- **제외 (MVP 이후)**: 외부 자원 직접 예약(API 미제공으로 원천적 불가), 결제, 전국 확장(서울 한정), 실시간 재고(외부 자원은 "확인 필요"로 명시)

## 2. 화면 설계

디자인 툴 없이 **HTML/CSS 정적 프로토타입 → React Native 컴포넌트**로 바로 진행했다. 1인 개발에서는 디자인 산출물과 실제 코드 사이 싱크가 깨지기 쉬워서, 처음부터 실제 렌더링되는 걸 보면서 다듬는 쪽을 선택했다.

- 화면 목록: 홈 / 지도 / 검색 / 상세 / 저장(북마크) / 마이
- 디자인 토큰(`src/theme/tokens.ts`)으로 색상·radius·spacing을 단일 소스로 관리해, 화면마다 값이 흩어지지 않게 함
- 진행 순서: 정적 목업(반복 수정) → 컴포넌트 분리(TopBar, ResourceCard, SectionIntro) → 실제 API 연동

## 3. DB 설계 (ERD 요약)

**PostgreSQL 15+ (PostGIS 확장)**. 선택 이유는 위치 기반 반경 검색의 정확도(`geography` 타입, 지구 곡률 반영)와, `ST_DWithin` 기반 GIST 인덱스 성능 때문. (부트캠프 표준은 MySQL이라 이 선택 자체가 포트폴리오에서 설명 포인트가 됨)

```
User ──┬── Reservation ──── RentalItem ──── Inventory
       ├── WaitlistEntry ─┘        │
       ├── FavoriteResource ─┐     └── Institution
       ├── NotificationSub ──┤
       └── ResourceReport ───┴──── PublicResource (source: SHARENURI / SEOUL_RESERVATION / BILLIM_PARTNER)
```

핵심 설계 결정 (면접에서 설명할 포인트):
1. `PublicResource`가 검색의 단일 진입점 — 외부 데이터와 자체 관리 데이터를 하나로 통합
2. `(source, externalId)` 유니크 제약으로 재수집 시 Upsert
3. `Inventory`/`Reservation`에 `@Version` 낙관적 락으로 동시 예약 방지
4. `gu`/`dong` 컬럼을 명시적으로 분리해 특정 구 하드코딩 실수 방지

## 4. API 명세

Swagger(`springdoc-openapi`)로 자동 생성, 실행 후 `/swagger-ui.html`에서 확인. 별도 문서 관리 없이 **코드가 곧 문서**가 되도록 함 — 1인 개발에서 문서와 코드가 따로 노는 걸 막는 가장 확실한 방법.

### 4.1 현재 구현된 엔드포인트
| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/v1/resources` | 전체 자원 목록 조회 |

### 4.2 계획된 엔드포인트
| 메서드 | 경로 | 설명 | 우선순위 |
|---|---|---|---|
| GET | `/api/v1/resources/{id}` | 단건 조회 | P0 |
| GET | `/api/v1/resources?category=&gu=&freeOnly=` | QueryDSL 동적 검색 | P0 |
| POST | `/api/v1/auth/login` | JWT 로그인 | P0 |
| POST | `/api/v1/favorites/{resourceId}` | 관심 자원 저장 | P1 |
| POST | `/api/v1/reservations` | 제휴 기관 물품 예약 | P1 |
| POST | `/api/v1/reports` | 정보 오류 제보 | P2 |
| GET | `/api/v1/admin/sync-logs` | 동기화 이력 조회(관리자) | P2 |

## 5. 개발 컨벤션 (1인 개발용으로 축소)

팀이 아니라서 PR 리뷰어가 없다. 대신:

- **커밋 메시지**: Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`) — 이미 적용 중
- **브랜치 전략**: 단순화한 GitHub Flow
  - `main`: 항상 실행 가능한 상태 유지
  - `feature/*`: 기능 단위 브랜치 → 완성되면 `main`에 머지
  - 리뷰어가 없어도 **PR을 만들고 스스로 머지**하는 습관 추천 — 커밋 히스토리가 기능 단위로 깔끔하게 남고, "왜 이렇게 짰는지"를 PR 설명에 남겨두면 나중에 면접 준비할 때 그대로 재사용 가능
- **기술 스택 확정 이유는 문서로 남긴다** — 이미 이 문서와 `00-DESIGN.md`가 그 역할

## 6. 인프라 초기 셋업

| 항목 | 상태 |
|---|---|
| GitHub 저장소 | ✅ 완료 (모노레포: `backend/`, `app/`) |
| Docker Compose(로컬 PostgreSQL+PostGIS) | ✅ 완료 |
| CI/CD (GitHub Actions) | ⬜ 예정 |
| 배포 환경 (AWS EC2/RDS) | ⬜ 예정 |
| Nginx 리버스 프록시 | ⬜ 예정 |

### 6.1 배포까지 남은 단계 (구체적 순서)
1. **AWS RDS(PostgreSQL+PostGIS) 생성** — 로컬 docker-compose 설정을 그대로 RDS 파라미터로 옮김
2. **EC2 인스턴스 준비** — 백엔드 JAR 실행 환경
3. **GitHub Actions CI 작성** — `main` push 시 `./gradlew test` 자동 실행 (배포 전 최소 품질 게이트)
4. **GitHub Actions CD 작성** — 테스트 통과 시 EC2로 JAR 배포 (SSH 또는 AWS CodeDeploy)
5. **Nginx 설정** — 80/443 포트를 8080(Spring Boot)으로 리버스 프록시, HTTPS는 Let's Encrypt
6. **환경변수 분리** — `application.yml`의 DB 비밀번호 등을 `application-prod.yml` + GitHub Secrets로 분리
7. **Expo EAS Build** — 앱은 별도로 EAS를 통해 스토어 제출용 빌드 생성

## 7. 마일스톤 (스프린트 대신 — 1인 개발 주간 목표)

2주 스프린트+회고 대신, **주 단위 목표 + 매주 일요일 셀프 체크**로 진행한다.

| 주차 | 목표 |
|---|---|
| 1주차 | 엔티티 설계, 서울시/공유누리 API 실데이터 확인, 어댑터 1차 구현 |
| 2주차 | 백엔드 프로젝트 실행 확인, 프론트(Expo) 기본 화면 구성, Git 초기 커밋 |
| 3주차 | 단건 조회 API, QueryDSL 검색 API 구현 |
| 4주차 | Spring Security + JWT 로그인, 관심 저장 API 연동 |
| 5주차 | 제휴 기관 예약·재고 동시성 구현 + 테스트 코드 (가장 좋은 면접 소재) |
| 6주차 | CI/CD 구성, AWS 배포 |
| 7주차 | 부하테스트(k6), 모니터링, 버그 수정 |
| 8주차 | 포트폴리오 문서화, 발표 자료 정리 |

칸반 대신 **GitHub Projects(무료)에 이 표를 그대로 옮겨서 Issue로 쪼개는 것**을 추천한다. 혼자 하더라도 칸반 보드로 진행 상황을 시각화해두면, 나중에 "일정 관리를 어떻게 했는지" 설명할 근거가 된다.

## 8. 개발 착수 순서 (실제 다음 액션)

기능 사이의 **의존성이 적은 것부터** 순서를 잡는다. 인증이 없어도 되는 조회 기능을 먼저 완성하고, 그 위에 "누가"가 필요한 기능(예약, 관심 저장)을 얹는 방식이다.

1. 공유누리 실데이터 연동 (독립적, 다른 것에 안 얽힘)
2. 단건 조회 API (상세 화면이 이걸 기다리고 있음)
3. QueryDSL 검색 API (검색 화면 완성에 필요)
4. Spring Security + JWT (그 다음부터 "누구의 예약인지" 구분 가능해짐)
5. 제휴 기관 예약·동시성 (인증이 있어야 "누가 예약했는지" 의미가 생김)
6. CI/CD → 배포
